HEC-RAS 2025 -- THE PREPARE CRUX -- reproduce the subgrid property-table run (ADR 0130)
=======================================================================================

WHAT THIS PROVES
  `ras prepare` computes the subgrid PROPERTY TABLES (cell elevation-volume +
  face elevation-area curves) -- the exact capability the 6.x Linux path lacked
  (ADR 0100 M3 STOP). This exercises that computation headless on Linux under the
  SUBSTITUTED open-source GDAL 3.11.5 + HDF5 natives (image hecras2025:subst-exp,
  ADR 0129) and proves it completes WITHOUT hitting HEC's 81 custom GDAL
  band-algebra / ComputedBand entrypoints.

WHY A HARNESS INSTEAD OF `ras prepare`
  `prepare -s <src>` requires a full valid .ras project (Project -> Plan ->
  Geometry(meshed) -> Terrain + NValue + BoundaryCondition) or it returns
  "Could not parse source" at the INPUT gate (never reaching any native code).
  The property-table computation is the STATIC method
  Geospatial.Vectors.Meshes.MeshPropertyTables.ComputeFrom(mesh, elevations,
  nValues, opts, out tables) -- called by prepare via
  Plan.TryPrepareCompute -> Geometry.PrepareForCompute ->
  FlowAreaLayer.ComputePropertyTables. The harness invokes that exact method
  directly, bypassing the on-disk .ras parse wall while exercising the identical
  native surface (terrain read via IResample.SamplePoints/Resample = substituted
  GDAL/HDF5).

CALL CHAIN (decompiled, Ras.Core + Geospatial.Core):
  ras prepare
    -> PrepareArgs.Execute  (Project.IsValidProjectFile | Plan.IsValid gate)
    -> Plan.TryPrepareCompute
       -> Geometry.PrepareForCompute
          -> FlowAreaLayer.ComputePropertyTables
             -> MeshPropertyTables.ComputeFrom  <-- THE CRUX (what the harness calls)
  RecomputeMesh (the `ras mesh` verb) does NOT compute property tables -- it only
  builds the mesh. Property tables are a PREPARE-stage computation.

INPUTS (in ./fixtures, all tiny, EPSG:26915, 32x32 @ 10 m, elev 100-124.8 m):
  tiny_dem.tif          synthetic DEM (source raster)
  elev.h5 (+ tile)      HEC terrain built by `ras createterrain -f tiny_dem.tif`
  nvalue_const.tif      constant Manning's n = 0.06 raster (same grid)
  nvalue.h5 (+ tile)    HEC terrain built from nvalue_const.tif (n-value surface)
  NOTE: rebuild elev.h5 / nvalue.h5 with createterrain IN the working dir so the
  stored tile path resolves; a terrain h5 carries its tile path and returns
  NoData everywhere if the tile is not found.

STEPS
  0. Source the beta DLLs for compile-time references (Private=false, runtime uses
     the app-dir copies):
        Ras.Core.dll, Geospatial.Core.dll, Geospatial.GDALAssist.dll, Utility.Core.dll
     -> place in a dir mounted at /dll.

  1. (Re)build the two terrains inside the subst image, writing into the mount so
     tile paths resolve:
        docker run --rm -v $PWD/work:/work --entrypoint bash hecras2025:subst-exp -lc '
          cd /opt/hecras2025/app
          dotnet ras.dll createterrain -f /work/tiny_dem.tif      -o /work/elev.h5   -j EPSG:26915
          dotnet ras.dll createterrain -f /work/nvalue_const.tif  -o /work/nvalue.h5 -j EPSG:26915 '

  2. Compile the harness (needs the SDK; the subst image has runtime only):
        docker run --rm -v $PWD/dll:/dll -v $PWD/harness:/src --entrypoint bash \
          mcr.microsoft.com/dotnet/sdk:9.0 -lc 'cd /src && dotnet build -c Release -o /src/out Harness.csproj'

  3. Run under the substituted natives (drop harness.dll beside the app assemblies;
     reuse ras.runtimeconfig.json so sibling assemblies + native GDAL resolve):
        docker run --rm -v $PWD/harness/out:/hout:ro -v $PWD/work:/work --entrypoint bash \
          hecras2025:subst-exp -lc '
            cp /hout/harness.dll /opt/hecras2025/app/harness.dll
            cp /opt/hecras2025/app/ras.runtimeconfig.json /opt/hecras2025/app/harness.runtimeconfig.json
            dotnet /opt/hecras2025/app/harness.dll /work/elev.h5 /work/nvalue.h5 8 8 '

EXPECTED (see 20_computefrom_success.txt):
  terrain.SamplePoints probe -> real elevations (e.g. 112.8, 111.2, 114.4)
  ComputeFrom returned. Result=True
  CellVolumeTable.len / CellElevationTable.len  (elevation-volume curves)
  FaceElevationTable.len / FaceAreaTable.len    (elevation-area curves)
  VERDICT: property-table computation completed without EntryPointNotFound.

  The mesh is INSET (RatioAroundCenter 0.80) inside the terrain extent so that
  perimeter-face sample points do not land on the terrain edge (edge points return
  NoData -> "Missing terrain data at Face N"; a data-boundary artifact, NOT a
  native wall).

ON-DISK TABLE SCHEMA (MeshReader.WriteTables, standard HEC-RAS layout):
  /Geometry/2D Flow Areas/<name>/  holds mesh + property tables as the classic
  ragged Info(start,count) + flat Values arrays -- same pattern as 6.x
  (Cells Volume Elevation Info/Values, Faces Area Elevation Info/Values,
  Face Mannings n). In-memory the harness reads:
    Cell : CellTableStart/CellTableCount + CellVolumeTable/CellElevationTable
    Face : FaceTableStart/FaceTableCount + FaceElevationTable/FaceAreaTable
           + FaceWettedPerimeterTable + FaceManningsTable
