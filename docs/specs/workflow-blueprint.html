Section A

The shape of a workflow

A workflow is a fixed spine of steps; templates supply values, never structure. Each step that touches an engine hands off to that engine's official library — we write the thin agnostic call, the library does the domain work. That is the whole idea; it does not need a pattern name.

Section B

Input vocabulary — descriptive, not a change

Nothing about how inputs are formatted, resolved, or stored changes: the resolved sheet, the doors, the journal, and rerun all stay exactly as they are. The five categories below are words for talking about inputs — what any simulation's input set looks like — useful in forms, docs, and gate conversation. They are not a schema and nothing gets re-categorized.

CategoryMeaning

Section C — the new construction

The mesh tool — a tool family like fetch

The winning pattern a third time: fetch = declarative specs + one router; styles = declarative presets + one seam; mesh = a parametric spec + a registry of named edit actions wrapping official mesher libraries. The policy zoo (MeshPolicy, CorridorPolicy, CatchmentPolicy) dies into spec fields; MeshArtifact stays as the convergence point. Meshers are libraries, not engines — one OceanMesh2D build feeds TELEMAC, SWAN and SCHISM alike, which is exactly why the mesh tool stands alone.

The signature — a declaration block, like DATA and PARAMS

# module level in the template, beside DATA and PARAMS — frozen, NOTHING builds at import
MESH = tool.build_mesh(
    mesher = "om2d",              # mesher: om2d | telapy_mesh | hecras | reg_grid
    kind   = "unstructured_tri",  # structured_grid | unstructured_tri |
                                  #   unstructured_quad_flex | curvilinear | node_link
    aoi    = P.aoi,               # or the workflow's domain
    refine = {"edge_length": P.edge_length, "min_spacing": 25, "gradation": 0.15},
    bed    = D.dem,               # bathymetry via the frozen fetch subsystem
).edit("add_obstacle", D.breakwaters)   # a DECLARED edit: the recipe's prefix

# the SAME tool called standalone (agent / user / driver) builds now and
# stashes the MeshArtifact in the case for discovery:
tool.build_mesh(mesher="om2d", kind="unstructured_tri", aoi=aoi, ...)

# at runtime, when the plan first demands MESH, a SESSION opens over the
# declaration; gate-time edits APPEND to the declared chain:
session.edit("set_boundary",  side="seaward", type="open")
session.edit("refine_region", geometry=harbor_poly, edge_length=10)
session.edit("restart")       # truncates back to the declared prefix
session.accept()              # -> MeshArtifact (.slf / .gr3 / fort.14 + MDAL display)

The edit-action registry — where all three surfaces converge

Each mesher registers named actions with typed inputs: thin hooks wrapping the library's own functions, never reimplementations. The router validates a spec and an edit against the registering mesher's declared fields, loudly — the bag is typed at the router, not by Python classes. And an action never cares who authored its inputs:

  • direct code and drivers call actions with params;
  • agent gets generated tools — one per registered action, mounted only while a MeshSession is open, unmounted on accept;
  • user-drawn (later) QGIS drawings deliver geometry into the same actions — the substrate under the future drawing surface already exists.

The gate loop

The recipe is the record

A mesh IS (spec + ordered edit chain), journaled like the run journal — deterministic rebuild by replay, restart truncates the chain, rerun and provenance come free. A QGIS hand-edit enters as one recorded action carrying the edited layer's hash: honest about being non-replayable, while everything around it still is.

mesh_recipe.jsonl
  {"spec": {"mesher": "om2d", "kind": "unstructured_tri", "refine": {...}}}
  {"edit": "add_obstacle",      "geometry": "sha256:…", "source": "fetch_osm_breakwaters"}
  {"edit": "set_boundary",      "side": "seaward", "type": "open"}
  {"edit": "apply_layer_edits", "layer": "sha256:…", "replayable": false}

Agent eyes

Every action returns numeric probes — node/element count, edge-length histogram, min-angle quality, boundary segments, obstacle count — and the session renders a wireframe snapshot the agent reads with vision (the proof render lane). The agent gets competent eyes; the human at the gate stays the final eye.

Supplied mesh + laziness (as ruled)

  • Explicit-first, discovery-second: an explicit mesh argument on the run always wins; otherwise the router discovers compatible MeshArtifacts already authored in the case and offers them at the gate; else the workflow's declared spec builds the default.
  • Demand-pull: the build fires when a downstream step first demands the artifact — the form stays cheap, refused runs cost nothing.

Section D

Where the QGIS translation lives

Split by audience.

  • mesh/ owns solver formats — .slf, .gr3, the HEC-RAS bundle: solver food.
  • emission owns the display face — domain mesh → MDAL-loadable layer. A mesh is just another data type on the one emission seam, exactly like rasters, vectors, and series. The .2dm writer moves out of generate_mesh onto the seam when the mesh wave lands.
The razor: if it feeds a solver, it is mesh/'s business; if it feeds a screen, it is emission's. One seam per audience, no third place.

Emission stays declarative (frozen subsystem)

No specialization per workflow or engine: products declare a quantity; styles.yaml resolves the look; .style() overrides declaratively; restyle_layer changes the display face only. The seam generalizes by data type, never by engine:

Section E

Class view — the mesh tool

The classes the mesh wave builds. Downstream of MeshArtifact, everything is today's machinery: the deck writers, the box dispatch, the emission seam. (Stepping via telapy is deliberately absent — the run paradigm as-is carries the spec; stepping arrives later for free.)
