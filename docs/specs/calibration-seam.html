1. The principle

A calibration sits between a finished run and its rerun. The user declares WHICH declared params may vary, within bounds, and WHICH fetched observations are compared to WHICH outputs. PEST++ (USGS) proposes; pyEMU builds its interface; our forward run is the existing rerun path; the result is a PROPOSED fill the user confirms. We own no loop mathematics, no run management, no optimizer. Every calibrated value is labeled as such wherever it is read.

2. The recipe: verbatim library calls over three rows

# templates/rain_on_grid/rain_on_grid.py - the template gains a calibration recipe (data, like MESH)
CALIBRATE = tool.calibrate(
    vary=[Vary(P.curve_number, bounds=(30, 100)),
          Vary(P.manning_multiplier, bounds=(0.5, 2.0), transform="log")],
    observe=[Observe(output="outlet_hydrograph", series=DATA.gauge, weight=1.0)],
    method="ies",                                      # ies | glm | sweep
    ops=[cal_op("pst_from_parnames_obsnames"),         # pyEMU names, verbatim
         cal_op("ParameterEnsemble.from_gaussian_draw", num_reals=50),
         cal_op("pestpp-ies", noptmax=3)],
)
rowisconstraint
Varya DECLARED Param (never a raw keyword) with bounds and an optional transformdeclared params enter the invocation key and carry bounds; a raw keyword does neither - a keyword-only variation can REPLAY the parent's solve, so the recipe refuses it by name
Observean OUTPUT the run publishes (a hydrograph, a station series) paired with a fetched SERIES (any DATA row that carries time_series_csv) and a weightunits and datum reconciled by the pairing tool's own rules; a series that states neither refuses by name
opsthe pyEMU and PEST++ calls, by their own names, in ordersignature-is-the-schema; unknown names refuse naming the library's
methodwhich PEST++ executable runs the loopies (ensemble, default), glm (Jacobian, single fit), sweep (a parameter grid)

actcontract
calibrate(run_id, recipe)builds the PEST++ interface with pyEMU (control file, a parameters template, an instruction file over sim.csv), stages a work dir, states the RUN BUDGET up front (runs x the measured forward wall) and refuses BudgetExceeded by name, runs the sensitivity pass, then the method. Serial by default; workers starts PEST++ worker processes (run ids and rundirs are ULIDs, so concurrency is a host-resource decision only).
forward_run.pythe model command PEST++ calls: a DRIVE-LANE script that reads the parameter file, calls rerun_workflow(parent, overrides={param: value}) (never a container of its own - the ADR 0319 grep is a standing test), maps an override EQUAL to the parent's value onto the parent's own result (the rerun path refuses an inert override; a Jacobian base run or a resampled equal draw is that case), reads the output, pairs it against the pinned observation on the observation's own stamps, DELETES then writes sim.csv so a failed run is a failed run, and journals one field, objective.
Proposal + confirmthe record: per varied param the posterior median and range, phi before and after, the posterior band of the observed output, the method and its settings. Rendered on the card as a PROPOSED column beside CURRENT; nothing is applied. confirm(proposal) is one more rerun whose varied slots carry provenance calibrated by <method> and basis calibrated.

5. Observation sources (the substrate, general purpose)

An Observe row reads any fetched series or extent. Three kinds of observation, all ordinary fetchers usable for anything, not calibration machinery: a POINT over time (a gauge), a PROFILE every ~21 days (SWOT), an EXTENT on a date (DSWx).

A 21-day repeat cannot see a storm hydrograph: rain_on_grid stays on the gauge. SWOT's place is the water-surface PROFILE along a reach (what constrains friction and bed on a wide river, gauged or not) and lake levels where no station exists. Its datum arithmetic is the datum rule's, unchanged.

7. Dependencies and where the loop runs

PEST++ is not on PyPI: its binaries land in bin/ through scripts/fetch_binaries.sh with a sha256 (the mf6 precedent). pyEMU installs into the daemon's venv once the pandas pin that blocks it leaves: that pin exists for hydromt-sfincs, an engine no longer in the tree (a lean-sweep row; the fallback is pyEMU 1.4). The PEST++ master is a daemon subprocess in a work dir under the runs directory; the 60 s sandbox is not the master. Two venvs are OUT of spec unless the pin cannot go.
