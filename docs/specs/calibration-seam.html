1. The principle

A calibration sits between a finished run and its rerun. The user declares WHICH declared params may vary, within bounds, and WHICH fetched observations are compared to WHICH outputs. PEST++ (USGS) proposes; pyEMU builds its interface; our forward run is the existing rerun path; the result is a PROPOSED fill the user confirms. We own no loop mathematics, no run management, no optimizer. Every calibrated value is labeled as such wherever it is read.

2. The recipe is filled at invocation, over every declared param

REV 2 (NATE 2026-09-09): a template carries NO calibration recipe - that would decide for the user which knobs may vary, the same pigeonhole the hardcoded author literals were. The VARIATION SURFACE is every declared Param with bounds, which the sheet already exposes. calibrate is a runtime act like fill: the user or the model names which params vary and which observation pairs with which output, from anything the sheet declares. A template may SUGGEST a default pairing the way it pre-fills slots (rain_on_grid: the outlet hydrograph against the nearest gauge), and the user overrides it exactly as a slot.

# at invocation - the same door as fill; every row is a declared Param, a published output or a fetched series
calibrate(run_id,
    vary=[Vary("curve_number", bounds=(30, 100)),
          Vary("manning_multiplier", bounds=(0.5, 2.0), transform="log")],
    observe=[Observe(output="outlet_hydrograph", series=DATA.gauge, weight=1.0)],
    method="ies",                                      # ies | glm | sweep
    ops=[cal_op("pst_from_parnames_obsnames"),         # pyEMU names, verbatim
         cal_op("ParameterEnsemble.from_gaussian_draw", num_reals=50),
         cal_op("pestpp-ies", noptmax=3)])
# templates/rain_on_grid: a SUGGESTED pairing only, data the user edits
CALIBRATION_DEFAULT = Pairing(vary=["curve_number", "manning_multiplier"], observe=("outlet_hydrograph", DATA.gauge))

actcontract
calibrate(run_id, recipe)builds the PEST++ interface with pyEMU (control file, a parameters template, an instruction file over sim.csv), stages a work dir, states the RUN BUDGET up front (runs x the measured forward wall) and refuses BudgetExceeded by name, runs the sensitivity pass, then the method. Serial by default; workers starts PEST++ worker processes (run ids and rundirs are ULIDs, so concurrency is a host-resource decision only).
forward_run.pythe model command PEST++ calls: a DRIVE-LANE script that reads the parameter file, calls rerun_workflow(parent, overrides={param: value}) (never a container of its own - the ADR 0319 grep is a standing test), maps an override EQUAL to the parent's value onto the parent's own result (the rerun path refuses an inert override; a Jacobian base run or a resampled equal draw is that case), reads the output, pairs it against the pinned observation on the observation's own stamps, DELETES then writes sim.csv so a failed run is a failed run, and journals one field, objective.
Proposal + confirmthe record: per varied param the posterior median and range, phi before and after, the posterior band of the observed output, the method and its settings. Rendered on the card as a PROPOSED column beside CURRENT; nothing is applied. confirm(proposal) is one more rerun whose varied slots carry provenance calibrated by <method> and basis calibrated.

3a. The variations record, and the ensemble primitive at the back end

THE PRIMITIVE is "launch N sims with these params and RECORD them", and it appears at two levels: plain execution uses it once; calibration wraps it in a loop with the intermediate step - evaluate the results and propose the next set - which PEST++ owns. This wave builds the launcher calibration needs: every forward run is an ordinary rerun (the mesh inherited, a unique run id) and EVERY MEMBER IS RECORDED in the run journal - the parent run, the varied params and their values, its own run id, its outcome, the objective - with one manifest per calibration naming its members and how they were generated (PEST++'s own par/obs files cited beside it). Any result traces to the exact variation that produced it; a finished calibration re-reads without re-running.

THE NEXT WAVE generalizes that launcher into an ensemble act on regular execution: a list, a grid or a draw of variations (pyEMU's ensemble draws; PEST++'s sweep executable for grids) run as concurrent reruns under a workers lever, recorded the same way, with no observation and no objective required. Monte Carlo ("what range of outcomes should I expect") and sensitivity sweeps are one pass of it; calibration is the loop. Its live proof is a twenty-draw Monte Carlo on rain_on_grid with the outlet-peak spread reported and every member traceable. OUT OF THIS WAVE, stated so the launcher is built to be lifted, not rewritten.

5. Observation sources (the substrate, general purpose)

An Observe row reads any fetched series or extent. Three kinds of observation, all ordinary fetchers usable for anything, not calibration machinery: a POINT over time (a gauge), a PROFILE every ~21 days (SWOT), an EXTENT on a date (DSWx).

5a. The STAC raster executor (rides in this wave; the migration is the next lean wave)

A raster served through a STAC catalog is loaded by odc.stac.load(items, bbox, crs, resolution, chunks) into an xarray and written by rioxarray as a COG. The fetcher tree's raster executor carries a hand-written VRT parser and a windowed multi-tile mosaic, and about forty per-source hooks carry tile ladders, mosaicking, reprojection and subsetting the library does in one call. RESEQUENCED (rev 1c, NATE 2026-09-08): the fetcher fold wave now runs BEFORE this wave and lands the one executor, stac-raster (~200 LOC), with its spec fields (collection, assets, bands, resolution, the catalog endpoint, the signing or token hook) and OPERA DSWx as its proving consumer; this wave INHERITS the executor and adds the SWOT fetchers on it - zero hook code either way. odc-stac and odc-geo are the two new dependencies (xarray, rioxarray, dask, zarr, pystac-client are already declared).

THE TRADE, stated: the fetcher transport owns retries, honors Retry-After and logs upstream errors verbatim; odc-stac reads through GDAL, which brings its own retry configuration and error channel. Stage 0 proves that a throttled or failing read under GDAL's retry settings logs the upstream message verbatim through rasterio's error channel; a failed cell holds the executor to signed reads only. THE MIGRATION of the existing raster and gridded hooks (3DEP, Copernicus, the topobathy ladder, BlueTopo, land cover, JRC, HRRR/AORC/gridMET/CHIRPS/MRMS over Zarr and NetCDF via xarray.open_zarr/open_dataset) and of the vector hooks (GDAL's OGR drivers, OSMnx, HyRiver) is that fold wave, hook by hook, on NATE's per-family rulings from the two-lens census.

7. Dependencies and where the loop runs

PEST++ is not on PyPI: its binaries land in bin/ through scripts/fetch_binaries.sh with a sha256 (the mf6 precedent). pyEMU installs into the daemon's venv once the pandas pin that blocks it leaves: that pin exists for hydromt-sfincs, an engine no longer in the tree (a lean-sweep row; the fallback is pyEMU 1.4). The PEST++ master is a daemon subprocess in a work dir under the runs directory; the 60 s sandbox is not the master. Two venvs are OUT of spec unless the pin cannot go.
