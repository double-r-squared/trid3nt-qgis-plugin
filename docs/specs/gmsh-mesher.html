2. How meshing works (primer)

  • Quality = triangle shape (minimum angle) + sizing h(x), the target-edge-length field. Sizing functions (distance-to-shore, wavelength, bathymetric gradient, gradation) are oceanmesh's specialty and permanent seat.
  • Generation: DistMesh relaxation (oceanmesh - iterative, measured nondeterministic), Delaunay/frontal insertion (gmsh/jigsaw - deterministic orders possible), structured grids (trivially deterministic).
  • Conformality: an outline is conformal when its vertices ARE mesh nodes; constraints must feed INTO generation (retrofit measured 80.1 m offset here) - why "edit" means "regenerate" across the field.
  • Cost: nodes ~ area/h²; screening meshes regenerate in seconds (measured) - regeneration is the economical common path; patch-local editing is a deferred design for measured large-mesh pain.
  • Boundaries: contiguous OPEN vs LAND stretches; IPOBO permutations, .cli rows, gr3 blocks - telapy's bookkeeping seat, the last mile for every mesh.

3. How data is used in a workflow - the model

One substrate, three facts:

  1. The AOI is threaded. One value (geocode or canvas), fed to every tool as the default spatial context. It is never mutated by anything.
  2. Tools all the way down. Fetchers, processing operations, the mesh builder, and workflows share ONE invocation substrate: each is declarable inside a template AND directly invocable (!run) in chat. A processing operation like delineation is just a tool whose output is a value.
  3. Derived values are named and passed explicitly. A tool's output becomes a named value (a plan ref in templates, a variable in chat) that downstream tools take as ordinary parameters. Explicit parameters ARE the dataflow - visible at the call site, journaled, nothing hidden, nothing aggregated.
# in a template - declared dataflow, every hop visible:
SUBDOMAIN = tool.process(P.aoi, "delineate", pour_point=P.pour_point)
MESH      = tool.build_mesh(extent=SUBDOMAIN, bed=D.dem, ...)   # derived extent
MESH      = tool.build_mesh(extent=P.aoi, bed=D.dem, ...)       # common case - STILL written out

# in chat - the SAME tools, ad hoc:
#   !run process aoi delineate pour_point=...   -> subdomain
#   !run build_mesh extent= ...           -> the mesh, right there

The reach dissolves into this model as named values with coupling by dataflow: flowline = fetch(aoi); seed = snap_to(flowline); discharge = read_at(seed) - meshing takes flowline, forcing takes discharge, the release gate validates on flowline. A gate-drawn value and a fetched value are the same argument; no tool cares who authored its inputs. (An earlier "grounding record" bundling these was REJECTED: inputs live in ONE place.)

4. The mesh declaration

MESH = tool.build_mesh(
    extent = P.aoi,                # WHERE to mesh - ALWAYS declared in templates:
                                   # one free line that keeps the context visible.
                                   # P.aoi = the threaded AOI (the common case);
                                   # a derived value (SUBDOMAIN) narrows, in plain sight
    kind   = "unstructured_tri",   # discretization - defaulted when obvious
    mesher = "auto",               # builder auto-routed from the constituents; pin to override
    for_   = "telemac",            # consumer contract - auto-injected in templates
    bed    = D.dem,                # constituents: ordinary data refs
    shoreline = D.shoreline,
    refine = {"edge_length": P.edge_length, "min_spacing": 25},
)
  • extent: the one spatial parameter, and templates ALWAYS declare it - even when it is just extent=P.aoi, because the line is free and the context is valuable (the reader answers "where does this mesh live?" from the declaration, never from a default rule). The AOI default exists only for standalone/chat convenience. Narrowing is always an explicit act (over-meshing wastes recoverable compute; premature narrowing loses unrecoverable correctness). Runtime change: re-run the deriving tool in chat and feed the result, or the set_extent session edit at the gate (journaled, basis=user, narrow or widen).
  • Capabilities from presence: bare extent -> refine_region, apply_layer_edits; + shoreline -> add_obstacle, set_boundary; + flowline -> corridor verbs, valid release areas; + pour_point -> catchment behavior (closed boundary). The only capability mechanism: unoffered verbs never mounted; direct calls refuse by naming the missing constituent; builders register per constituent pattern, refused at import unless the pattern's verbs are implemented.
  • Sourcing is DATA-first in templates (declared ladders, gate visibility, journaling); in-tool "fetch:" specs are standalone sugar through the same router.
  • No words that imply: no domain labels anywhere - "coastal" is TRUE when bed + shoreline are present, never said.

4.1 The containment rule - what an extent change costs

An extent change is judged by GEOMETRIC CONTAINMENT against the STAGED COVERAGE (the footprint the fetches actually staged over):

new extentpathwhat happens
within coverageCROP - a cheap, journaled set_extent session editno refetch: rasters crop, vectors clip, the mesh rebuilds over the new extent; fetched inputs stand, only mesh-downstream recomputes
outside coverage (moved, or even slightly larger)RESTAGE - not an edit: the change escalates to rerun with the new bboxa box that leaves coverage is a NEW AOI, and everything anchored to the old one is suspect (the flowline may not be in the new box; seed and discharge hang off it). The existing rerun-with-overrides primitive computes the invalidation cut and re-resolves from the beginning. The gate says so honestly: "the drawn area leaves fetched coverage - this becomes a fresh run over the new area."

Containment is BINARY - no fuzzy tolerance: partial coverage produces silently wrong answers at the edge (mesh nodes outside the DEM footprint have no bed; boundary segments outside the shoreline clip misclassify). Crop is only safe when coverage is total. OPTIONAL refinement (NATE's call): stage fetches with a small declared buffer over the AOI so the common slight-outward nudge stays on the crop path; the test stays binary against the buffered coverage.
